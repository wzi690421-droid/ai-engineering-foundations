# ONNX Runtime C++ FP32 基线报告

日期：2026-08-17

## 测量对象

- 模型：CIFAR-10 `SmallCNN`
- ONNX：动态 Batch、FP32、114019 bytes
- 后端：ONNX Runtime 1.28.0 `CPUExecutionProvider`
- 输入：RGB `[N, 3, 32, 32]`

## 环境

- CPU：Intel Core i7-12700H，20 个逻辑 CPU
- 系统：Linux 7.0.0-28-generic
- 编译器：G++ 13.3.0，C++17
- OpenCV：4.6.0
- ONNX Runtime：1.28.0

## 测量边界

纯推理基线只测：

```text
OnnxModel::run()
```

包含 Tensor 包装、ONNX Runtime 推理和输出复制；不包含模型加载、图片读取、预处理、Top-K 和 CSV 写入。

端到端基线测：

```text
imread/解码/预处理 → OnnxModel::run() → Softmax/Top-K
```

每组先 warm-up 10 次，再正式测量 100 次。CSV 写入发生在计时结束后。

## 纯推理 Batch 对比

下表为每个 Batch 重复 5 轮后的轮均值：

| Batch | mean 延迟（ms） | p50（ms） | p95（ms） | 吞吐（images/s） | 单张有效计算时间（ms） |
|---:|---:|---:|---:|---:|---:|
| 1 | 0.034564 | 0.034101 | 0.037584 | 28941 | 0.034564 |
| 2 | 0.042774 | 0.042070 | 0.046767 | 46779 | 0.021387 |
| 4 | 0.087403 | 0.062572 | 0.072753 | 53697 | 0.021851 |
| 8 | 0.085243 | 0.084993 | 0.089347 | 94048 | 0.010655 |

Batch=4 的两次原始测量出现约 3.086 ms 的异常值，因此 mean 和平均吞吐受到明显影响；p50 更接近其典型延迟。

Batch=8 相比 Batch=1：

- 平均吞吐提高约 3.25 倍；
- 处理同样 8 张图片时，p50 批处理加速约 3.21 倍；
- 单次请求计算延迟从约 0.034 ms 增加到约 0.085 ms；
- 在线场景还需额外考虑凑 Batch 的排队时间。

## Batch=1 端到端分段结果

5 次独立进程实验中，各轮端到端指标的中位数为：

| 指标 | 延迟（ms） |
|---|---:|
| run-level mean 中位数 | 0.108955 |
| run-level p50 中位数 | 0.109206 |
| run-level p95 中位数 | 0.116736 |

典型阶段占比约为：

| 阶段 | 占比 |
|---|---:|
| 图片读取、解码和预处理 | 约 60% |
| ONNX Runtime 推理 | 约 38% |
| Softmax/Top-K | 约 2% |

当前端到端主要瓶颈是图片读取与预处理。即使把模型推理时间降低一半，端到端加速也只有约 1.23 倍；即使模型推理时间降为 0，按该占比计算的理论最大端到端加速也约为 1.59 倍。

## 峰值内存

使用 `/usr/bin/time -v` 测量整个进程的 Maximum RSS：

| Batch | Maximum RSS |
|---:|---:|
| 1 | 74028 KiB（约 72.29 MiB） |
| 8 | 73820 KiB（约 72.09 MiB） |

两者没有显著差异。当前峰值主要来自 Runtime、动态库、线程池和模型会话；32×32 的小输入 Tensor 对进程峰值影响很小。

## 结论与限制

1. warm-up 能排除第一次推理的明显冷启动开销。
2. 同一进程内 Batch=1 的稳态重复实验变异系数约 0.8%，但独立进程之间仍会受到系统负载影响。
3. 该模型极小，几十微秒的推理容易受到调度、CPU 主频和后台任务影响，必须同时保留原始数据、p50、p95 和多轮结果。
4. 图片被反复读取后会进入操作系统页面缓存，因此端到端结果更接近热缓存读取，不代表首次冷磁盘读取。
5. 当前使用 ONNX Runtime 默认线程设置，没有固定 CPU 核心、线程数或 CPU 主频；这些变量留给下一阶段做受控实验。
